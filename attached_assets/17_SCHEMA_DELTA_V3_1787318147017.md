# Schema Delta Required by v3 Direction

This is an implementation contract, not a mandatory SQL migration script. Adapt it to the current Replit schema without destroying existing data.

## Required identity additions

Add or confirm support for:

### `player_external_ids`
Suggested fields:
- canonical `player_id`
- `source_id`
- `external_id`
- `confidence`
- `valid_from`
- `valid_to`
- provenance/audit metadata

Unique constraint should prevent one source external ID from mapping to multiple active canonical players unless explicitly versioned/resolved.

### `player_aliases`
Suggested fields:
- `player_id`
- raw alias
- normalized alias
- source
- observed_at

### `identity_match_events`
Store evidence and matching algorithm/version for audit.

## Starter history

Probable/official starter state is time-varying. Preserve observations rather than only the latest state.

Support:
- CONFIRMED
- PROBABLE
- TBD
- OPENER
- BULK
- UNKNOWN

## Lineup history

Expand lineup states to support at least:
- PROJECTED
- POSTED
- UPDATED
- SCRATCHED
- UNKNOWN

Preserve each observed snapshot and source.

## FantasyPros snapshots

Add or confirm:
- projection snapshot header
- projection rows
- source player ID
- canonical player ID nullable until mapping resolves
- raw stats JSON
- normalized stats JSON
- effective date
- retrieval timestamp
- ingest run

Older snapshots are immutable.

## Four-market enum/type

Support canonical values:
- TOTAL_BASES_2_PLUS
- EXTRA_BASE_HIT
- BATTER_WALK
- HOME_RUN

Do not encode sleeper/primary as separate market types. Those are future ranking/display roles, not settlement definitions.

## Prediction tables — future compatibility

Prediction rows should be able to store:
- market
- model version
- research/feature snapshot
- predicted probability when validated
- confidence status
- lineup snapshot reference
- bullpen snapshot reference
- source freshness summary
- frozen timestamp

Do not require odds snapshot foreign keys.

If an old `odds_snapshot_id` exists, make it nullable/optional and ensure no core workflow requires it.

## XBH settlement support

Future settlement should store component outcomes separately:
- singles
- doubles
- triples
- home runs
- total bases
- walks

Then derive XBH hit from:

`doubles + triples + home_runs >= 1`

Do not settle XBH from total bases alone.

## Data Health issues

Support issue categories:
- IDENTITY_CONFLICT
- GAME_STATE_CONFLICT
- STARTER_CONFLICT
- LINEUP_CONFLICT
- SOURCE_FAILURE
- STALE_SOURCE
- NORMALIZATION_FAILURE
- DUPLICATE_ENTITY
- MISSING_REQUIRED_FIELD

## Legacy odds tables

Do not drop legacy odds data destructively if it already exists.

Mark it optional and isolate it from current prediction/readiness logic.
